01

Introduction

Claude is an AI assistant developed by Anthropic. 2550 Engineering has adopted Claude on the Team plan to help staff work more efficiently — writing code, drafting documents, analysing data, researching topics, and automating repetitive tasks.

This guide explains how to get started, what the key features are, how to connect Claude to our internal tools, and how to use Claude safely within the boundaries 2550 Engineering has agreed.

Claude Products

Your account gives access to several Claude products under one login:

💬
Claude Chat
Web-based AI chat at claude.ai. Ask questions, write content, review code, analyse documents.
🖥
Desktop & Mobile
Native apps for macOS, Windows, iOS, Android. Linked folder access and richer features.
⌨
Claude Code
Terminal/IDE tool for coding tasks. Delegates implementation, refactoring, and debugging.
⚙
Claude Cowork
Agentic task runner — automates multi-step workflows and coordinates background agents.
🎨
Claude Design
Visual design canvas — create UI mockups, landing pages, posters, and multi-artboard layouts that you can edit by hand and export.
⚠ Claude Design — Token Usage

Claude Design sessions are token-intensive. Under the Team plan, a single complex design session can consume a significant portion of your daily token allowance. Be mindful when using it for large or iterative designs — your session may use up your limit quickly. If you hit your limit mid-session, you will need to wait until your allowance resets before continuing.

ℹ Data & Privacy

On the 2550 Engineering Team plan, Anthropic does not use your conversations to train its models. Your prompts and outputs are processed by Anthropic infrastructure but are not retained for model training. See Section 7 for the full picture.

What Are Claude Skills?

Skills are packaged sets of instructions and domain knowledge that make Claude behave as a specialist for specific tasks. Think of them as expert-mode presets — a skill loads best practices and task-specific guidance so Claude handles that type of work more effectively without you re-explaining everything from scratch.

How Skills Work

How it activatesDescription
AutomaticClaude detects what you are working on and applies the relevant skill. Ask for a chart and the dataviz skill activates without you doing anything.
Slash commandType /skill-name to explicitly invoke a skill — e.g. /docx for Word document creation, /pdf for PDF tasks.
Via CoworkWhen you assign a task in Cowork, Claude applies relevant skills automatically to inform how it approaches multi-step work.

How to Install Skills

Skills are accessed through the Customize panel — not directly in Settings. Look for the Customize button at the very bottom of the left sidebar (below your conversations list).

  1. Open Claude at claude.ai or in the desktop app.
  2. Click Customize at the bottom of the left sidebar.
  3. Select the Skills tab in the Customize panel — you'll also see Connectors and Plugins tabs here.
  4. Click Discover to browse available skills from the marketplace, or Your skills to see what you already have installed.
  5. To add a skill, click the Add button (top right of the panel). A dropdown appears with options: Upload skill, Create a skill, Create with Claude, or Record your screen.
  6. Once added, skills activate automatically based on your task — or you can call one explicitly by typing /skill-name in a conversation.

Technical Insight: How Skills Are Built

Skills are structured folders containing a SKILL.md instruction file and optionally supporting reference materials. They follow a standard format that works across Claude Chat, Cowork, and Claude Code. Users can place skill folders in ~/.claude/skills/ for local use, or install them via the Skills marketplace.

Anatomy of a Skill

Every skill is defined by a single Markdown file with two parts: a YAML frontmatter block (metadata Claude and the UI use to identify and describe the skill) and a plain-English instruction body (what Claude actually reads and follows when the skill is active).

---
name: code-reviewer
description: Reviews code for quality, clarity, and security issues. Use when
  asking Claude to review a pull request, function, or module.
---

# Code Review Skill

You are a thorough, constructive code reviewer. When asked to review code:

## What to check
- **Correctness** — Does the logic handle edge cases and error conditions?
- **Clarity** — Is the code readable? Would a new team member understand it?
- **Security** — Are there obvious vulnerabilities (SQL injection, unvalidated
  input, exposed secrets)?
- **Performance** — Are there any clearly inefficient patterns for the scale
  this code will run at?
- **Tests** — Are the key paths covered? Are assertions meaningful?

## How to respond
Structure your review as:
1. A one-sentence overall verdict (approve / approve with comments / request changes)
2. Numbered findings, each with: location, issue, why it matters, suggested fix
3. A short "what's working well" note — point out good patterns, not just problems

Be specific and reference line numbers or function names where possible.
Keep your tone direct but constructive — assume the author cares about quality.

## What NOT to do
- Do not rewrite the whole function unless asked
- Do not flag style issues that Black or a linter would catch automatically
- Do not suggest architectural changes in a routine PR review

How the Frontmatter Works

The name field is the skill's identifier — this is what you type as /code-reviewer to invoke it directly. The description field is what Claude reads to decide whether to activate the skill automatically; write it as a single sentence that names the task the skill handles and the signal words that trigger it.

How to Create Your Own Skill

  1. Open the Customize panel (bottom of the sidebar) and select the Skills tab.
  2. Click Add → Create a skill (or Create with Claude to have Claude draft it for you based on a description).
  3. Write your SKILL.md — start with the frontmatter block, then describe the behaviour you want in clear plain English. Include examples of good and bad outputs if the standard is non-obvious.
  4. Save and test: open a new conversation, describe a task the skill should handle, and check whether Claude applies it correctly. If not, refine the description or add a concrete example to the instruction body.
💡 Tip: The most effective skill instructions read like a well-written brief to a competent colleague — they explain what good looks like, not just what to do. Include a short "what NOT to do" section if there are common failure modes worth ruling out explicitly.

Skill Scope

Skills you create in the Your skills tab are personal — only you see them. Org admins can publish skills to the whole 2550 Engineering team, making them appear in everyone's library. If you build a skill that would be useful across the team (a 2550 coding standards reviewer, a sprint retrospective formatter, etc.) share it with your Claude admin to get it deployed org-wide.

What Are Claude Connectors?

Connectors extend Claude's capabilities by giving it access to external tools and data sources. They are powered by the Model Context Protocol (MCP) — an open standard created by Anthropic that provides a unified way for AI applications to interact with services.

Types of Connectors

TypeExamplesHow to add
Prebuilt (first-party)Google Drive, Gmail, Google Calendar, GitHub, Slack, Microsoft 365One-click via Customize → Connectors
Directory (third-party)17+ pages at claude.com/partners/mcpCustomize → Connectors → Directory
Custom (MCP URL)Any service with an MCP endpointCustomize → Connectors → Add Custom

How to Install a Connector

Like Skills, Connectors are found under the Customize panel — click Customize at the bottom of the left sidebar, then select the Connectors tab.

⛔ Admin approval required: At 2550 Engineering, connector requests must be approved by a group admin before they become active. Do not attempt to connect services that haven't been approved — contact your Claude admin to request access to a new connector.
  1. Click Customize at the bottom of the left sidebar.
  2. Select the Connectors tab.
  3. Browse the Discover view or search for the service you need.
  4. Click the connector and follow the authentication prompts (OAuth or API token) — Claude only gets access to what you grant at this step.
  5. Your request will be sent to a 2550 Engineering admin for approval. You'll be notified once it's active.
  6. Once approved and connected, use the + button in any chat to pull in context from that service.

LabelWhat it means

You can block specific actions a connector can take. For example, allow a GitHub connector to read repositories but block it from creating or deleting them:

  • Go to Settings → Connectors.
  • Select the connector.
  • Find individual tools and set any to Blocked that you do not want Claude to use.

Setting Up Claude Rules & Instructions

What Are Project Instructions?

Project Instructions are a persistent set of rules and context written in plain English that apply to an entire Claude Project. Claude reads these at the start of every conversation in that project, so you never have to re-explain your context, tech stack, preferences, or constraints.

How to Set Project Instructions

  1. Open your project in Claude.
  2. Look for the Project Instructions panel in the sidebar or project settings.
  3. Type your instructions in plain English — no special syntax required.
  4. Click Save — instructions take effect immediately on the next conversation.

What to Include

TypeExample instruction
Tech stack"Stack: Python 3.12, FastAPI, PostgreSQL, Stripe. All monetary values use the Decimal type."
Tone & style"Concise, technical tone for senior engineers. British English. No marketing language."
Domain fencing"Only discuss topics related to internal engineering workflows. Politely decline anything else."
Data handling"Do not reproduce or transmit content from uploaded documents to any external service."
Confirmation gates"Before any irreversible action (deleting data, pushing to a shared branch), ask me to confirm."
Output format"Format code with language tags. Always include a Risks & Caveats section for architectural decisions."

Recommended Template for 2550 Teams

Copy and adapt for your project:
You are a helpful engineering assistant at 2550 Engineering. Context: - This project relates to: [describe your domain briefly] - Tech stack: [list relevant technologies] - Team: [e.g. Backend Engineering, Platform, Data] Rules: - Only assist with tasks related to this project's domain. - Do not share, transmit, or publish company data externally. - Do not take irreversible actions without asking for confirmation first. - If unsure about my intent, ask for clarification before acting. - Respond in British English. - When reviewing code, focus on: correctness, testability, performance, type safety. Output: - Format code with language tags. - Include a Risks and Caveats section for significant architectural decisions. - Keep responses concise and technical unless I ask for more detail.

Best Practices

  • Be specific — vague instructions produce vague behaviour. More context leads to better results.
  • State what Claude should not do, not just what it should do.
  • Iterate — update instructions as the project evolves. They take effect on the next conversation.
  • Combine with uploaded documents: instructions tell Claude how to behave; documents tell it what to know.

Creating Projects & Scopes

What Are Claude Projects?

Projects are self-contained workspaces inside Claude. Each project has its own conversation history (grouped and searchable), a knowledge base of documents you upload, and custom instructions that persist automatically.

This solves the "cold start" problem — you set your context once and Claude always knows it, without repeating yourself in every new chat.

How to Create a Project

  1. Open Claude at claude.ai or in the desktop app.
  2. Click Projects in the left sidebar, or the + New Project button.
  3. Give it a clear, descriptive name — e.g. "Backend API — Billing Service" or "Platform Incident Runbooks".
  4. Add your Project Instructions (Section 5).
  5. Upload relevant documents to the knowledge base.

What to Add to Your Knowledge Base

  • Architecture diagrams and decision records (ADRs)
  • Runbooks and incident playbooks
  • Style guides and coding standards
  • API documentation or OpenAPI specs
  • Past work samples or reference implementations

Documents are indexed and Claude references them automatically in every conversation within the project. The context window holds approximately 500 pages; paid plans extend this significantly with retrieval.

Team Collaboration

  • Click Share inside the project.
  • Add team members by email or name.
  • Set permission level: Can view (read-only) or Can edit (add documents, update instructions).
  • To revoke access, return to the Share panel and remove the member.

Recommended Project Structure at 2550

Project nameSuggested use
[Team] — [Service/Domain]Per-team, per-service project. E.g. "Backend — Billing Service". Keeps context scoped.
Architecture ReviewsShared space for cross-team design discussions. Upload ADRs, RFCs, diagrams.
Incident RunbooksOperational knowledge base — upload runbooks, then use Claude to help navigate incidents.
Code Review AssistantInstructions scoped to code review only. Upload your team's coding standards.

ℹ One Project Per Domain

Keep each project scoped to one team or domain. Mixing contexts in one project reduces quality. Creating separate projects for separate concerns is the primary mechanism for keeping Claude focused on approved tasks.

Safe & Responsible Use

This is the most important section. It applies to everyone, regardless of technical background.

Data Privacy Facts

QuestionAnswer
Does Anthropic train on my conversations?No. Under the 2550 Engineering Team plan commercial terms, Anthropic does not use your conversations or content to train its models.
What data is sent to Anthropic?Your prompts, Claude's responses, uploaded files, and usage metadata (timestamps, token counts) are processed by Anthropic's infrastructure.
How long is data retained?Conversations removed from the UI are purged from Anthropic's back-end within 30 days.
Is my data encrypted?Yes. Encrypted in transit and at rest. SOC 2, ISO 27001, GDPR, and CCPA compliant.

What You Must Not Do

🚫 Prohibited Actions — Read Carefully
  • ✗Upload PII, customer data, medical records, or any regulated data without confirming data handling agreements are in place with your admin.
  • ✗Ask Claude to publish, post, share, or transmit any 2550 Engineering information to external services — including public GitHub repos, social media, or third-party websites.
  • ✗Share API keys, passwords, authentication tokens, or credentials in a Claude conversation.
  • ✗Ask Claude to bypass, circumvent, or disable any security controls, authentication mechanisms, or access management systems.
  • ✗Attempt to jailbreak Claude or override its safety guidelines. This violates Anthropic's Acceptable Use Policy and 2550 Engineering's policy, and may result in account suspension.
  • ✗Use Claude output in high-stakes decisions (legal, financial, production deployments) without human review. Claude can make mistakes.
  • ✗Generate deceptive content — fake commit messages, fabricated test data presented as real results, or documentation that misrepresents what code does.

Keeping Claude Scoped to Approved Tasks

  • Create a Project with clear instructions that define what Claude should and should not help with (Sections 5 and 6).
  • Only connect Connectors from the approved list for your team.
  • Do not grant Claude access to services, files, or data beyond what your specific task requires.
  • If Claude suggests taking an action that feels outside its approved scope, decline it and report it to your Claude admin.

Always Review Before Acting

⚠ Human Review Required For:
  • Code before it is merged to a shared branch or deployed to production
  • Security assessments, penetration test findings, or vulnerability reports
  • Legal or compliance analysis
  • Financial calculations or models
  • Architecture decisions that affect shared systems
  • Any Claude-generated output that will be shared externally

Reporting Concerns

  • Use the thumbs-down button on any Claude response to send feedback directly to Anthropic.
  • Contact your Claude admin directly with a description of what happened — do not include sensitive content or credentials in any report.
  • For anything urgent or security-related, escalate to your team's Claude admin immediately.

If Claude refuses a request you believe is legitimate, reach out to your admin — do not attempt to find workarounds.

Example Project Setup

The best way to understand Claude Projects is to see one built from scratch. Below is a realistic walkthrough for a software engineer joining a backend team — but the same pattern applies to any discipline: product management, data analysis, technical writing, and more.

The Scenario

You're a backend engineer on the Orion platform — a B2B SaaS product built with Python, FastAPI, and PostgreSQL, deployed on AWS ECS. You want Claude to be a reliable pair-programmer and documentation helper that already knows your stack, your conventions, and your terminology.

Step 1: Create the Project

In Claude's left sidebar, click + New Project and give it a clear, specific name — something like "Orion API — Backend Engineering". A specific name keeps it distinct from other projects as your list grows.

Step 2: Write Your Project Instructions

Open the project, find the Project Instructions field, and write in plain English. Below is an example you can adapt:

You are a senior Python engineer helping build and maintain the Orion platform —
a B2B SaaS API built with FastAPI 0.115, SQLAlchemy 2.0, Alembic (migrations),
and PostgreSQL 15. Deployed on AWS ECS via Terraform.

CONVENTIONS
- Python 3.11. PEP 8, Black for formatting. Type hints are mandatory.
- Tests use pytest with fixtures in conftest.py. Aim for 80%+ coverage.
- API responses always use: { "data": ..., "meta": { "request_id": ... } }
- Errors follow RFC 7807 (Problem Details format).
- Feature flags via LaunchDarkly — never gate features directly in code.
- Do not suggest upgrading dependencies unless I ask.

HOW TO RESPOND
- Always explain *why* before suggesting a code change.
- Prefer SQLAlchemy ORM over raw SQL unless there's a clear performance reason.
- If something is ambiguous, ask one clarifying question before answering.
- Keep code examples realistic — use our naming conventions (snake_case, plural
  model names like "users", "invoices").
- Flag anything that could affect database migrations or production data.
💡 Tip: You don't need to write everything at once. Start with 5–6 key constraints and add more as you notice Claude making assumptions you'd rather it didn't.

Step 3: Add Knowledge to the Project

Upload the documents Claude should always have access to. For an engineering project, this might include your OpenAPI spec (as a YAML or PDF), your team's coding standards doc, an architecture overview, or your onboarding guide. Claude will use these as reference material throughout every conversation in the project.

Step 4: Your First Conversation

Here's what a first conversation might look like in this project — notice how Claude's response reflects the instructions without you having to repeat them:

You
I need to add a GET /invoices/{invoice_id} endpoint. It should return a single invoice for the authenticated user, or a 404 if not found. The Invoice model has fields: id, user_id, amount, currency, status, created_at.
Claude

Here's a FastAPI endpoint following your conventions. A few decisions I'm making — let me know if you'd prefer something different:

  • Using get_current_user as the auth dependency (assuming you have this already — adjust the import if it's named differently)
  • Scoping the query to user_id so users can't access each other's invoices, and returning 404 either way (avoids confirming whether an invoice exists)
  • Wrapping the response in your standard { "data": ..., "meta": ... } envelope
from fastapi import APIRouter, Depends, HTTPException
from sqlalchemy.orm import Session
from app.db import get_db
from app.auth import get_current_user
from app.models import Invoice, User
from app.schemas import InvoiceResponse, StandardResponse

router = APIRouter()

@router.get("/invoices/{invoice_id}", response_model=StandardResponse[InvoiceResponse])
def get_invoice(
    invoice_id: int,
    current_user: User = Depends(get_current_user),
    db: Session = Depends(get_db),
) -> StandardResponse[InvoiceResponse]:
    invoice = (
        db.query(Invoice)
        .filter(Invoice.id == invoice_id, Invoice.user_id == current_user.id)
        .first()
    )
    if not invoice:
        raise HTTPException(status_code=404, detail="Invoice not found")
    return StandardResponse(data=InvoiceResponse.from_orm(invoice))

Migration note: No schema changes needed — this is read-only. You'll want a pytest fixture for a test invoice seeded to your test user.

Want me to write the pytest test for this too?

You
Yes please, and also add a test for the 404 case.
Claude
import pytest
from fastapi.testclient import TestClient

def test_get_invoice_returns_invoice(client: TestClient, auth_headers, seed_invoice):
    response = client.get(f"/invoices/{seed_invoice.id}", headers=auth_headers)
    assert response.status_code == 200
    data = response.json()["data"]
    assert data["id"] == seed_invoice.id
    assert data["status"] == seed_invoice.status

def test_get_invoice_returns_404_for_missing(client: TestClient, auth_headers):
    response = client.get("/invoices/99999", headers=auth_headers)
    assert response.status_code == 404

def test_get_invoice_cannot_access_other_users_invoice(
    client: TestClient, auth_headers, other_user_invoice
):
    response = client.get(f"/invoices/{other_user_invoice.id}", headers=auth_headers)
    assert response.status_code == 404  # not 403 — avoid confirming existence

I've included a third test for the cross-user access case — worth having since that's a common security gap. You'll need a other_user_invoice fixture in conftest.py that seeds an invoice belonging to a different user.

What Made This Work

Claude didn't need to be told about the response envelope, the 404-not-403 pattern, or the testing conventions — the Project Instructions carried all of that. Over time, as you notice Claude making assumptions you'd rather it didn't, add a line to your instructions and it will apply to every future conversation in the project.

Adapt this for any role: A product manager might set instructions like "Always structure requirements with a problem statement, success criteria, and out-of-scope list." A data analyst might write "We use dbt, Snowflake, and Python. Always use CTEs rather than subqueries. Flag any query that could be slow on a 100M-row table."

Hints & Tips

Small habits make a big difference with Claude. These tips are drawn from Anthropic's prompting guidance and practical experience — they apply whether you're drafting an email or building a complex workflow.

01

Be specific and direct

Claude works best when you say exactly what you want. Instead of "Can you help with this email?" try "Rewrite this email to be more concise and professional, keeping it under 150 words." The more context you give, the better the result.

02

Explain the why, not just the what

Telling Claude the reason behind a request improves the output. Instead of "Don't use bullet points," say "Write in flowing paragraphs — this will be read aloud in a presentation." Context shapes how Claude interprets your instructions.

03

Give Claude a role

Starting with a role focuses Claude's tone and approach. Try: "You are an experienced technical writer — help me document this API." Or: "Act as a sceptical reviewer and critique this proposal."

04

Use examples to guide the format

If you want output in a particular style or structure, show Claude an example. Paste in a sample email, a past report, or a preferred format and say "Write it like this." Examples are one of the most reliable ways to control output style.

05

Break big tasks into steps

For complex work, don't try to do everything in one prompt. Ask Claude to draft an outline first, then expand each section. Or use a Project where you can build on previous conversations with shared context.

06

Ask Claude to check its own work

You can ask: "Review your answer and flag anything you're uncertain about" or "Before finishing, double-check the numbers in your summary." Claude can self-review effectively when explicitly prompted to do so.

07

Tell Claude what to do, not what to avoid

Positive instructions work better than negative ones. Instead of "Don't make it too long," try "Keep the response to 3 short paragraphs." Instead of "Don't be formal," try "Use a friendly, conversational tone."

08

Use Projects to keep Claude on-task

Set up a Project for your team or domain with specific instructions — e.g. "Always refer to our product as Orion" or "Responses should follow our tone of voice guide." Claude will apply these consistently across every conversation in that project.

09

Paste in the relevant context

Claude doesn't automatically have access to your files, emails, or systems. Copy in the relevant paragraph, code snippet, or data — the more focused the input, the more useful the output. Use Connectors for ongoing access to live tools like Google Drive or Jira.

10

Iterate — don't start over

If Claude's first response isn't quite right, follow up in the same conversation rather than starting again. Say "That's close — can you make it shorter and lead with the recommendation?" Claude remembers the full conversation and can refine from there.

11

Call a skill directly with /skill-name

If you know a skill exists (e.g. dataviz or docx), activate it by typing /dataviz or /docx at the start of your message — useful when Claude doesn't pick it up automatically from context.

Workflow Example

Claude is most powerful when you treat it less like a search engine and more like a capable colleague you brief properly before handing over work. The workflow below reflects how experienced users get the most out of it — and it applies whether you're writing a report, building software, or designing a presentation.

Step 1 — Set Up a Scoped Project First

Before starting any significant piece of work, create a dedicated Claude Project (Section 6). Give it a specific name and write Project Instructions (Section 5) that tell Claude exactly what it's helping you with: the stack, the conventions, the output style, the things to avoid. A well-briefed project means you don't repeat yourself across conversations — Claude already knows the context when you open a new chat.

Think of it as onboarding Claude to your project. The time you spend writing good instructions pays back immediately — every conversation in that project benefits from them automatically.

Step 2 — Be Explicit About the Output Format

Claude can produce many different kinds of output, and it will do a far better job if you tell it exactly what you need. Before asking Claude to produce something, decide: what format should the result be in? Some options to consider:

  • Claude Code prompts — if you're handing the work to Claude Code (the terminal-based coding agent), ask Claude to generate a ready-to-paste prompt you can use there. This is often the most effective way to translate a high-level idea into working code: Claude (chat) writes the engineering brief, Claude Code executes it.
  • Claude Design prompts — similarly, ask Claude to write a detailed design brief for Claude Design or another design tool, describing the layout, palette, and component structure.
  • A structured document — PDF, Word doc, or a formatted Confluence page. Telling Claude the destination format (e.g. "format this as a Confluence wiki page with headings and a table") changes how it structures the output.
  • A checklist or decision matrix — useful when you need to review options rather than act on a single answer.
💡 Get Claude to write the prompt

One of the most effective patterns: ask Claude (in a chat window) to write a detailed prompt for Claude Code to implement something. Claude understands its own capabilities and will produce a better-specified brief than most people would write by hand. Then paste it into Claude Code and let it run.

Step 3 — Use Plan Mode Before You Commit

Before Claude takes any significant action — writing a large amount of code, restructuring a document, sending an output somewhere — use Plan mode. In Plan mode, Claude describes exactly what it intends to do and asks for your confirmation before proceeding. This lets you:

  • Catch misunderstandings early, before Claude does unnecessary work.
  • Understand Claude's approach and redirect it if needed.
  • Review the plan with a colleague before approving execution.
  • Feel confident that irreversible actions (deleting files, posting content) have a human checkpoint.

To enter Plan mode, type /plan at the start of your message, or ask Claude to "describe what you'd do before doing it." Get comfortable with this habit — it saves significant time and avoids having to undo things.

Step 4 — Always Verify the Output

Claude is capable but not infallible. Treat its output as a first draft — review it before acting on it, publishing it, or committing it to a codebase. The right verification method depends on the work:

  • Code: run it, read it, test it. A second AI tool can help — Cursor and GitHub Copilot are well-regarded for reviewing Claude-generated code. They may catch different things because they use different models. Using multiple AI tools in combination is a reasonable professional practice.
  • Documents and plans: read them. Ask a colleague to review the logic, especially for anything that will be shared externally or used to make decisions.
  • Data or research: check the sources. Claude can hallucinate citations or misremember details — verify anything you plan to rely on.
⚠ Never skip review on high-stakes outputs

Code going to production, documents with legal or financial implications, and anything shared externally should always have a human review step — regardless of how confident Claude sounds.

Step 5 — Run Multiple Chats in Parallel

You are not limited to one Claude conversation at a time. Experienced users routinely keep several windows open — the browser app and the desktop app can run side by side, giving you two visible Claude sessions at once. This opens up useful parallel workflows:

  • While Claude writes code or a document in one tab, use another tab to verify facts, search for references, or prepare the next task.
  • Set a long or intensive task running in one window — something that will take Claude several minutes to work through — then switch to a second window and keep working on something else while you wait.
  • Use one chat for high-level planning (writing the brief, deciding the approach) and a separate project-specific chat for execution, so your planning conversation stays clean.
  • Keep a "scratchpad" chat open for quick questions, lookups, or experiments that you don't want polluting your main project context.
Browser + Desktop = two simultaneous views. Open Claude in your browser and keep the desktop app on your second monitor. You get two Claude sessions visible at the same time with no tab-switching.

APPENDIX A · TECHNICAL

Technical Reference

Model Context Protocol (MCP)

Connectors in Claude are powered by MCP — an open standard from Anthropic for connecting AI models to external tools and data. If your team wants to build a custom connector for an internal service:

  • Any service can expose an MCP server using the open spec at modelcontextprotocol.io.
  • Custom connectors are added in Claude via Settings → Connectors → Add Custom MCP URL.
  • For org-wide deployment, connectors can be packaged as plugins distributed via the admin console.

Plugins vs Skills vs Connectors

ConceptWhat it isAnalogy
ConnectorTechnical access to an external service (credentials, API endpoint). Powered by MCP.A key that opens a door
PluginA bundle of connector(s) + skill(s) + slash commands. Packages everything for a workflow.A toolbox for a specific job
SkillInstructions that tell Claude how to approach a class of tasks. A component inside a plugin.An expert briefing

Project Instructions as System Prompts

Project Instructions are implemented as system prompts — the top-level instruction layer in Claude's trust hierarchy:

Anthropic training → Operator system prompt (Project Instructions) → User messages

This means Project Instructions are an effective governance tool. A well-written instruction set reliably shapes Claude's behaviour across all conversations in a project. See Section 5 for the template.

Claude Code Integration

  • Install skills via ~/.claude/skills/ or the CLI.
  • Set project-level configuration in a CLAUDE.md file at the root of your repository — this acts as the system prompt for Claude Code sessions in that directory.
  • Configure MCP servers in .claude/mcp.json for project-specific tool access.
⚠ Claude Code and Credentials

Claude Code operates with access to your local filesystem and shell. Never store credentials, .env files with production secrets, or sensitive config in directories where Claude Code is active unless those files are correctly excluded. Use .gitignore and .claudeignore as appropriate.
